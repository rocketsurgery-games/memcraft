The left click that locks the pointer (`controls::grab_pointer`) is sometimes also seen by `targeting::edit_blocks` as a break click, so capturing the mouse breaks whatever the crosshair is on. Seen intermittently in headless drives (chest-1's CHEST stage, herd's re-run on af1c65a: total edits 1 where the stage made 0). menu-2 noted the ordering dependence earlier: Resume edits nothing only because `edit_blocks` runs before `grab_pointer`.

Fix the rule: a click that changes the lock state must not also act in the world (e.g. `edit_blocks` ignores buttons pressed in a frame where the pointer was unlocked at frame start, or a `JustLocked` marker), independent of system order. Related: mem-99d0 (left-button mouse lock, shorn).

Verify: a unit/app test that a lock click edits nothing regardless of system order; drive.js plain run and CHEST stage report 0 total edits across several runs.

▸ 2026-11-02T05:39:30Z [lockfix-1]

Decision: rule lives in controls as WorldMouse (a ButtonInput mirror holding only presses that began locked, until released), filled in PreUpdate after InputSystems so the lock state is read as of frame start, before grab_pointer/menu/dialogs can change it; edit_blocks (break/place) and pick_block read it, and the .before(grab_pointer) ordering is dropped. On wasm 'locked' also requires document.pointerLockElement: closes the async-grant window (a click before the page grants the lock is ignored) and the stale window after Esc (click before the app notices the dropped lock). Rejected: a JustLocked marker set by grab_pointer (only covers clicks that go through grab_pointer, not Resume / UI buttons, and depends on ordering); frame-start snapshot only (does not cover held presses or the async browser lock); a grace timer (guessy). Kept is_locked check in edit_blocks as belt and braces.
